# AGENTS.md

Guidance for AI coding agents working on this repository. For human contribution
rules (CLA, PR process, AI-assisted contribution policy), see [CONTRIBUTING.md](CONTRIBUTING.md).

## Project overview

Testing toolkit for the Google Maps SDK for Android, split into focused modules
covering fast headless JVM unit testing, deterministic offline golden screenshot
testing, and multimodal AI visual testing.

| Module | Purpose |
| --- | --- |
| `robolectric-testing` | Robolectric shadows for `MapView`, `GoogleMap`, `SupportMapFragment`, markers, shapes, and tile overlays, plus KTX test harness (`withTestMap` / `createTestMap`), Kotlin Power-Assert helpers (`assertMap` / `assertMarker` / `assertGeo`), and Google Truth subjects (`assertThat(map)`) |
| `golden-testing` | Deterministic offline golden image screenshot testing (`GoldenTileProviders`, `rememberGoldenTileProvider`, `GoldenImageDiff`, `assertMatchesGolden`) |
| `visual-testing` | Multimodal AI visual testing powered by Google Gemini Vision (`BaseVisualTest`, `GeminiVisualTestHelper`, hybrid golden fallback, and UiAutomator natural-language actions) |
| `app` | Demo and sample application exercising the Maps SDK and all three testing modules |
| `docs` | Dokka multi-module API documentation aggregation |

## Building and testing

```bash
./gradlew assembleDebug                                # build everything
./gradlew :robolectric-testing:testDebugUnitTest       # unit tests for one module
./gradlew test                                         # all JVM unit tests
./gradlew koverXmlReportDebug                          # all unit tests and coverage reports
./gradlew lint                                         # Android Lint across all modules
./gradlew apiCheck                                     # public API matches the committed api/*.api files
./gradlew spotlessCheck                                # verify license headers and code formatting
./gradlew docs:dokkaGenerate                           # generate multi-module Dokka HTML docs
./gradlew connectedAndroidTest                         # run instrumentation tests on attached device/emulator
```

Coverage is tracked over time. After every merge to `main`, the
`Record coverage history` workflow appends a row per module per suite to
`history.csv` and regenerates `COVERAGE.md`, both of which live on the
[`coverage-history`](../../tree/coverage-history) branch. They are generated by
`.github/scripts/coverage_history.py`. Never edit them by hand.

The data is kept off `main` deliberately. Branch protection on `main` uses
strict required status checks, so any commit pushed there marks every open
pull request out-of-date and forces contributors to update their branch and
re-run CI. Keeping coverage data on its own branch means recording it costs
contributors nothing.

Two suites are recorded separately, because they instrument different code and
cannot be merged from their XML reports:

| Suite | Produced by | Covers |
| --- | --- | --- |
| `unit` | `koverXmlReportDebug` | the three published library modules (`robolectric-testing`, `golden-testing`, `visual-testing`) |
| `instrumentation` | `connectedAndroidTest` (emulator) | modules owning `androidTest` sources (`app`, `golden-testing`, `visual-testing`) |

Instrumentation coverage is not re-measured after merge; the post-merge
workflow reuses the artifact from the pull request's emulator run, so no extra
emulator time is spent. If the run fails, is missing, or does not finish within
the wait window, only unit coverage is recorded for that commit.

Running `:app` on a device or running live Gemini Vision checks in
`:visual-testing` requires API keys in `secrets.properties` at the repo root
(`MAPS_API_KEY=...` and optionally `GEMINI_API_KEY=...`). Without
`GEMINI_API_KEY`, `:app:connectedDebugAndroidTest` automatically uses the
offline test APK golden baselines under `app/src/androidTest/assets/goldens/`.
Never hardcode or commit API keys.

## Agent setup

This file is the shared instruction set for every coding agent. `CLAUDE.md`
and `GEMINI.md` only import it, and Codex and Copilot read it directly, so put
new guidance here rather than in a tool-specific file.

Skills live in `.agents/skills/`. `.claude/skills` and `.gemini/skills` are
symlinks to that folder, so edit the files under `.agents/skills/` only:

- `.agents/skills/android-maps-testing/SKILL.md`: Umbrella guide covering the
  Testing Pyramid decision matrix, CUJ decomposition, and architecture rules.
- `.agents/skills/maps-robolectric-testing/SKILL.md`: Headless JVM testing with
  `:robolectric-testing` (KTX harness, Truth subjects, Power-Assert, Java).
- `.agents/skills/maps-golden-testing/SKILL.md`: Deterministic offline golden
  screenshot testing with `:golden-testing`.
- `.agents/skills/maps-visual-testing/SKILL.md`: Multimodal AI visual testing
  and hybrid golden fallback with `:visual-testing`.

`release-please` bumps the version lines in these skill files automatically on
each release.

## Code style

- Format code and verify license headers with `./gradlew spotlessApply` /
  `./gradlew spotlessCheck`.
- Match the language and idiom of the file you are editing; new code is Kotlin
  unless it extends an existing Java shadow API surface.
- Do not use wildcard imports (`import foo.*`); use explicit top-level imports.
- Do not use inline fully qualified class names (FQCNs) inside code bodies;
  declare explicit imports at the top of the file and resolve name collisions
  with import aliases (`import foo.Bar as BarAlias`).
- Published library modules (`robolectric-testing`, `golden-testing`,
  `visual-testing`) target **Java 11** (`JavaVersion.VERSION_11`,
  `JvmTarget.JVM_11`) to preserve compatibility with downstream consumers on
  Java 11 toolchains. Do not upgrade published library bytecode to Java 17
  without explicit approval.
- Provide KDoc/Javadoc on all public classes, properties, and functions; API
  documentation is published via Dokka.
- Surround code snippets that are referenced in documentation or skills with
  region tags (`// [START <tag>]` ... `// [END <tag>]`) so documentation and
  samples remain synchronized with compiled source code.
- Avoid `!!` in production library code where null-safe operators or explicit
  preconditions (`requireNotNull`, `checkNotNull`) clarify intent.
- Public API changes must be additive and backward compatible; deprecate before
  removing.
- The public API of each library is committed in `<module>/api/<module>.api` and
  checked by `apiCheck` in CI. After an intentional API change, run
  `./gradlew apiDump` and commit the updated file, so the change is visible in
  review. The check compares binary signatures, so also look out for renamed
  parameters, which break callers using named arguments.

## Pull requests

- Use Conventional Commit messages (`feat:`, `fix:`, `docs:`, `chore:`,
  `build(deps):`, `test:`, `refactor:`, `perf:`). `release-please` parses them
  to generate versions and `CHANGELOG.md`; a wrong prefix causes a wrong
  release bump. Never edit `CHANGELOG.md` or `.release-please-manifest.json` by
  hand.
- **Several changes in one PR**: a squash merge keeps only the PR title, so
  `release-please` would list one entry. When a PR contains several changes
  that belong in the changelog separately (for example several features or bug
  fixes), add a commit override block at the end of the PR description, one
  Conventional Commit per line. `release-please` uses these lines instead of
  the PR title:

  ```
  BEGIN_COMMIT_OVERRIDE
  feat(robolectric): add View.findMapView() hierarchy lookup extension
  feat(golden): add 1-liner GoogleMap.assertMatchesGolden extension
  END_COMMIT_OVERRIDE
  ```

  The PR title still has to be a valid Conventional Commit. Each line counts
  for the version bump, so a `feat:` or `!` line bumps accordingly.
- Keep a pull request to what its title says. Once review has started, put new
  features or unrelated fixes in a separate pull request. If the scope does
  change, update the type in the title, since `release-please` reads it.
- Answer every review thread before asking for another review: push the change,
  or reply in the thread with why not.
- Never commit anything that only makes sense on your machine or inside Google:
  local paths (`file:///`, `/Users/...`, workstation home directories),
  `go/` links, `b/` bug IDs, or API keys. The `Agent leftovers` check fails the
  pull request on these, and on AI co-author trailers and links to agent chat
  sessions.
- Every behavior change needs a unit test in the affected module.
- All pull requests are to be created as drafts (`gh pr create --draft`) until
  authorization is explicitly given to mark them ready for review. Always
  inform the user that the PR was created as a draft.
- Run `./gradlew test lint spotlessCheck docs:dokkaGenerate` before declaring
  work done, and report actual results.
- Do not add dependencies to the library modules without discussion in an issue
  first; the libraries are consumed by downstream apps and dependency weight
  matters.
- AI tools must not be listed as authors or co-authors on commits or PRs, and
  unsolicited bot-generated PRs are prohibited (see [CONTRIBUTING.md](CONTRIBUTING.md)).
